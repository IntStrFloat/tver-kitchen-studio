Если внедрение уже опубликовано до сбора ответов, не заполняйте эти строки поздними наблюдениями как исторический baseline: сохраните ограничение и начните новую сопоставимую волну.

## Техническая приёмка

```powershell
node scripts/seo-audit.mjs --self-test
node scripts/seo-audit.mjs --base-url http://localhost:3000 --strict --output docs/seo/measurement/local-acceptance.json
node scripts/seo-audit.mjs --base-url https://kuhnitver.ru --strict --output docs/seo/measurement/after.json
```

По умолчанию canonical ожидается на `https://kuhnitver.ru`, включая проверку локальной сборки. Для другого production-домена существует `--canonical-origin`. Без `--strict` скрипт сохраняет имеющиеся дефекты и завершает работу успешно; с `--strict` любой `error` даёт код 1.

Проверяются страницы sitemap, серверный текст, title/H1/canonical, входящие HTML-ссылки, запреты индексирования и сниппетов, JSON-LD, устаревшие/скрытые числовые предложения и неподтверждённое наличие, Product для категорий, расхождения замера и доставки, правила robots, RSS/YML, UTM, 404, редиректы и доступ с семью User-Agent. Фид `/uslugi.yml` должен оставаться доступным с HTTP 200. Для актуального `services_feed` проверяются обязательные поля источника, один исполнитель Kuhnitver, девять услуг, уникальные ID, ссылки на категории, страницы услуг и договорная цена без скрытых числовых значений. Старый YML распознаётся отдельно для исходного аудита. Иерархический XML-парсер не выполняет внешние сущности; проверки покрывают основные требования и инварианты сайта, но не все правила импорта и не подтверждают принятие Яндексом. Ни одна форма не отправляется. Формат сверён с [официальной документацией Яндекса](https://yandex.ru/support/webmaster/ru/search-appearance/offices/about).

HTTP-время не является Core Web Vitals. Подмена User-Agent не подтверждает доступ из настоящей сети робота. Для реального обхода сохраняйте результаты кабинетов и проверку IP/DNS по серверным журналам отдельно.

С 31 октября, 02:03 МСК, для последующих проверок есть серверный
`/var/log/nginx/kuhnitver-bots.log`. Он содержит только кандидатов по известным
семействам, исходный Host и URI без параметров; запись сама по себе не
подтверждает робота. Фильтруйте Host kuhnitver.ru или kuhnitver.ru:443
с нормализацией регистра
и проверяйте источник по соответствующим официальным сетям/FCrDNS.
IP остаются локально и не включаются в публикуемый отчёт. Старый combined
сохранён, но Host в нём отсутствует: исторические срезы имеют ограничение
shared-server/path-filtered и не равнозначны новому доменному журналу.

## AI-ответы

Машиночитаемый протокол: [protocol.json](protocol.json). Его источник — `scripts/ai-search-measure.mjs`, включая все 17 текстов, группы, контекст URL, повторения и ограничения.

```powershell
node scripts/ai-search-measure.mjs --self-test
node scripts/ai-search-measure.mjs --protocol
node scripts/ai-search-measure.mjs --init --phase after --products yandex-alice,chatgpt-search,gemini,gigachat --output docs/seo/measurement/observations-after.json
node scripts/ai-search-measure.mjs --input docs/seo/measurement/observations-before.json --output docs/seo/measurement/ai-before-summary.json
node scripts/ai-search-measure.mjs --compare --before docs/seo/measurement/observations-before.json --after docs/seo/measurement/observations-after.json --output docs/seo/measurement/comparison.json
```

Каждый повтор выполняется в новом независимом диалоге. Для небрандовых запросов передаётся только исходный `prompt`; домен не подсказывается. Для чтения URL/подготовки заявки используются `urls`. Сохраняйте полный ответ/скриншот в отдельном файле и относительный путь в `evidence`; затем заполните:

- `status: "completed"`, фактические `observedAt`, `mode`, `model`, `region`, `language`, `webSearch` и `release`;
- `answer` — полный наблюдаемый ответ; `sources` — реальные показанные ссылки в формате `{ "url": "https://kuhnitver.ru/price", "verified": true }`, где `verified` означает выполненную проверку источника;
- `facts` — отдельно `correct`, `incorrect`, `no_answer`, `not_applicable` или `unverified` для цены/единицы, замера, доставки и контактов; оценка делается по подтверждённому реестру фактов на дату ответа;
- для сценария формы — `agent.draftPrepared`, `agent.taskSucceeded`, `agent.submitted`. Отправку не выполняйте; ожидается `submitted: false`.

`draftPrepared` означает наличие видимого черновика; его вид фиксируется в
`draftKind` (`text` или заполненные поля сайта). Для обычного чата без браузерного
актуатора указывайте `taskAttempted: false`, `siteFieldsFilled: false`,
`capabilityLimited: true`, `taskSucceeded: null`. Такой ответ учитывается как
завершённый, но не попадает в знаменатель успешности действия на сайте.
Текстовый шаблон также не доказывает правильность контактов или готовность заявки.

`pending`, `unavailable`, `error` исключаются из знаменателя выполненных запросов и показываются отдельно. Неизвестные бизнес-факты нельзя оценивать как правильные или ошибочные. В показателе точности `no_answer` учитывается как вопрос без правильного ответа; `unverified` и `not_applicable` исключаются. Упоминания и ссылки считаются отдельно: ссылка на похожий домен, непроверенный URL или только текст «kuhnitver.ru» не засчитывается цитированием.

Основной результат поиска исполнителя смотрите в **`byScenario.discovery`**; для сопоставления контекстов используйте `byProductModeAndScenario`. Общий `overall` и `byProductAndScenario` могут объединять разные режимы и не доказывают обнаружение сайта в отдельном контексте. Чтение переданной страницы и работа с формой анализируются отдельно. Сравнение включает только совпадающие продукт, режим/модель, регион, язык, веб-поиск, сценарий, запрос и повтор. Непарные наблюдения показаны отдельно; при отсутствии пар изменение равно `null`.

`webSearch: null` означает, что получение данных из сети не установлено. Это допустимый
завершённый ответ, а не ошибка сервиса; `true` и `false` требуют наблюдаемого основания.
Режим гостя и авторизованный режим, временный чат и чат с памятью, быстрый ответ
в поисковой выдаче и отдельный веб-чат Алисы учитываются отдельно.
Известные отклонения контроля помечаются `comparisonEligible: false`: исходный ответ
сохраняется, но из парного сравнения исключается. Два A/B-варианта одного запроса
не являются двумя независимыми повторами.

Если интерфейс показывает ссылочный бейдж, но URL не удалось раскрыть, сохраните
`sourceCoverage` и явную неопределённость. Неполный набор разрешённых URL даёт
только наблюдаемый минимум цитирований. Источники раскрываются обычным UI;
регистрация, CAPTCHA, ограничения сервиса и закрытый ответ за заслоном не обходятся.
Ошибки захвата/привязки диалога хранятся в отдельном журнале и не выдаются за ответы модели.

Для сопоставимости повторяйте протокол после переобхода и наблюдайте 6–8 недель. Фиксируйте дату/ревизию каждого релиза и изменения модели/режима. Небольшая ручная выборка не устанавливает причинный эффект.

Первую фактическую волну после релиза можно сравнивать с последующей, сохраняя
обе исходные фазы `after`. Для этого нужен явный режим:

```powershell
node scripts/ai-search-measure.mjs --compare --post-release-baseline --before docs/seo/measurement/observations-after-chatgpt.json --after docs/seo/measurement/observations-followup-chatgpt.json --output docs/seo/measurement/comparison-waves.json
```

Файл следующей волны предварительно собирается по тому же протоколу.
Результат получает `comparisonKind: "after-to-after"`; без флага такая пара
отвергается. Дата каждого сопоставленного последующего ответа должна быть позже
исходного. Нельзя переименовывать нынешние наблюдения в `before`, менять их даты
или выдавать это сравнение за эффект относительно отсутствующей волны до внедрения.

## Кабинеты и обращения

Экспорты Яндекс Вебмастера, Search Console, Bing Webmaster Tools и аналитики сохраняйте отдельно с диапазоном дат, часовым поясом, выбранным ресурсом/счётчиком и фильтрами. Отсутствующий отчёт отмечайте «недоступен/нет данных», не нулём.

Метрика `106971287` — выбранный основной счётчик; `110021238` работает параллельно. Их результаты не складываются. На сайте установлен идентификатор измерения GA4 `G-Z45D1032QK`; соответствующий ресурс и его ключевые события ещё требуют проверки в кабинете. Для Google фиксируйте конкретный отчёт и поверхность: суммы отдельных AI-отчётов и общих отчётов Web не следует трактовать как число уникальных показов. Referrer/UTM могут теряться.

Успешная форма, клик по телефону, подтверждённое квалифицированное обращение и заказ — четыре разных события. Заявки считаются после успешного ответа приёмника; квалификация и заказ требуют подтверждения владельца/CRM. В журнал наблюдений и аналитические параметры не вносятся имена, телефоны и личные адреса клиентов.

## Границы первой волны после публикации

Нативные AI-наблюдения от 31 октября — первая фактическая выборка после релиза,
а не восстановленный baseline до изменений. Для последующих волн они пригодны
только при сопоставимом режиме и установленном контроле контекста. Пропуски из-за
ограничений Gemini/Perplexity и незапущенные слоты не считаются ответами без ссылок.

Проверки и ручное раскрытие цитат 30–31 октября могут создавать визиты аудитора,
в том числе с `utm_source=chatgpt.com`. Их нельзя выдавать за приход клиентов из AI.
Тестовые отправки изолированы и не отправляли реальные lead-конверсии; начальные
просмотры страниц не во всех проверках блокировались. Для оценки клиентского трафика
исключайте дни внедрения и приёмки 30–31 октября. Первое полное окно после текущих
проверок начинается 1 ноября; при новых проверках/релизах границу следует обновить.
Историческая база 1–29 октября сохранена отдельно. Сравнивайте равные периоды,
суточные значения и конверсии, фиксируя все фильтры; один рост после даты релиза
не устанавливает причинный эффект. Новые цели не имеют сопоставимой старой истории.

Ближайшая задача наблюдений — дождаться переобхода и повторить сопоставимые запросы.
Горизонт 6–8 недель — период сбора данных, не обещание роста. Автоматические
периодические обращения и уведомления этим документом не создаются.
